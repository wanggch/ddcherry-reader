# 桌面客户端架构设计

> 讨论范围：如何基于当前 Markdown Reader Pro 浏览器扩展，发展出同时支持 macOS 与 Windows 的桌面客户端，并保证后续新功能能够一处开发、多端生效。
> 
> 本文档为设计稿，不修改现有项目代码。

---

## 1. 目标与范围

### 1.1 目标

- 在保留现有浏览器扩展的基础上，新增 macOS / Windows 桌面客户端。
- 新功能优先在共享核心中实现，浏览器扩展与桌面客户端同步受益。
- 降低跨平台维护成本：核心渲染、主题、配置逻辑只写一次。

### 1.2 范围

- **包含**：代码组织、共享边界、核心接口设计、构建发布流程、版本策略、迁移路线。
- **不包含**：具体 UI 设计、品牌视觉、商店上架文案、收费模式。

---

## 2. 总体架构原则

```text
┌─────────────────────────────────────────────────────────────┐
│                     平台无关的共享核心                        │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │  Markdown   │  │    主题     │  │       配置          │  │
│  │   渲染管线   │  │  CSS / 变量  │  │  schema / 默认值    │  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │    TOC      │  │  图片预览   │  │   Raw / Preview     │  │
│  │  生成/滚动   │  │  灯箱组件   │  │     切换逻辑         │  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
   ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
   │  浏览器扩展壳  │     │  桌面客户端壳  │     │  未来其他壳   │
   │  Chrome/Edge │     │ Electron/   │     │  (CLI/TUI)  │
   │   Firefox   │     │    Tauri    │     │             │
   └─────────────┘     └─────────────┘     └─────────────┘
```

核心原则：

1. **共享核心，分离壳层**：渲染、主题、通用 UI、配置 schema 进核心包；平台生命周期、文件系统、存储实现留在壳里。
2. **依赖倒置**：核心包通过接口调用平台能力，不直接依赖 `chrome.*` 或 `node:fs`。
3. **统一测试**：核心逻辑在核心包里测试；壳只测平台特有逻辑。

## 4. 核心包接口设计

核心包只暴露平台无关的 API，平台能力通过接口注入。

### 4.1 文件访问接口

```ts
// packages/core/src/file/provider.ts

export interface FileInfo {
  path: string;
  name: string;
  extension: string;
}

export interface FileContent {
  content: string;
  encoding: 'utf-8';
  lastModified?: number;
}

export interface FileProvider {
  /** 读取文件完整内容 */
  readFile(path: string): Promise<FileContent>;

  /** 监听文件变化，返回取消监听函数 */
  watchFile(path: string, callback: () => void): () => void;

  /** 解析相对资源路径（图片、附件等） */
  resolveAssetPath(filePath: string, assetRelativePath: string): string;

  /** 判断路径是否可读 */
  canRead(path: string): Promise<boolean>;
}
```

浏览器扩展实现：

```ts
// packages/extension/src/adapters/chrome-file-provider.ts

import type { FileProvider, FileContent } from '@md-reader/core';

export class ChromeFileProvider implements FileProvider {
  async readFile(path: string): Promise<FileContent> {
    const res = await fetch(path);
    if (!res.ok) throw new Error(`Failed to read ${path}`);
    return { content: await res.text(), encoding: 'utf-8' };
  }

  watchFile(path: string, callback: () => void): () => void {
    // 浏览器扩展无原生文件监听，使用轮询兜底
    const interval = setInterval(async () => {
      // 通过比较 lastModified 或 ETag 触发 callback
      callback();
    }, 2000);
    return () => clearInterval(interval);
  }

  resolveAssetPath(filePath: string, assetRelativePath: string): string {
    const base = filePath.substring(0, filePath.lastIndexOf('/') + 1);
    return new URL(assetRelativePath, base).href;
  }

  async canRead(path: string): Promise<boolean> {
    try {
      const res = await fetch(path, { method: 'HEAD' });
      return res.ok;
    } catch {
      return false;
    }
  }
}
```

桌面端实现：

```ts
// packages/desktop/src/main/file-service.ts

import { readFile, stat, watch } from 'node:fs/promises';
import { resolve, dirname } from 'node:path';
import type { FileProvider, FileContent } from '@md-reader/core';

export class NodeFileProvider implements FileProvider {
  async readFile(path: string): Promise<FileContent> {
    const buffer = await readFile(path);
    const stats = await stat(path);
    return {
      content: buffer.toString('utf-8'),
      encoding: 'utf-8',
      lastModified: stats.mtimeMs,
    };
  }

  watchFile(path: string, callback: () => void): () => void {
    const watcher = watch(path, (event) => {
      if (event === 'change') callback();
    });
    return () => watcher.close();
  }

  resolveAssetPath(filePath: string, assetRelativePath: string): string {
    return resolve(dirname(filePath), assetRelativePath);
  }

  async canRead(path: string): Promise<boolean> {
    try {
      await stat(path);
      return true;
    } catch {
      return false;
    }
  }
}
```

## 6. 桌面客户端壳设计

### 6.1 技术选型建议

| 方案 | 推荐场景 | 初步判断 |
|---|---|---|
| **Electron** | 快速验证、团队熟悉前端、需要丰富生态 | 最稳妥，与现有 JS 代码完全兼容 |
| **Tauri** | 追求小体积、愿意引入 Rust、长期维护 | 安装包可降至 < 10MB |
| **WebView2 + 原生** | Windows 为主，mac 为辅 | 不建议，跨平台成本最高 |

**建议**：先用 Electron 做 MVP 验证市场和体验；稳定后评估是否迁移到 Tauri。

### 6.2 桌面端独有能力

- 注册 `.md`、`.markdown`、`.mdx` 文件关联。
- 系统右键菜单："用 Markdown Reader Pro 打开"。
- 最近打开文件列表（JumpList / Dock 菜单）。
- 原生文件监听（`fs.watch` / `notify`）。
- 菜单栏：文件、视图、主题、导出 PDF。
- 自动更新。

### 6.3 文件关联配置示例（Electron）

```json
// packages/desktop/package.json
{
  "build": {
    "fileAssociations": [
      {
        "ext": ["md", "markdown", "mkd", "mdx", "txt"],
        "name": "Markdown",
        "description": "Markdown document",
        "icon": "assets/file-icon.icns"
      }

```

### 6.4 进程通信（Electron）

```ts
// preload / IPC 封装
contextBridge.exposeInMainWorld('mdReader', {
  openFile: (path: string) => ipcRenderer.invoke('file:open', path),
  watchFile: (path: string) => ipcRenderer.invoke('file:watch', path),
  onFileChanged: (cb: () => void) => ipcRenderer.on('file:changed', cb),
  getPreferences: () => ipcRenderer.invoke('prefs:get'),
  setPreferences: (prefs: object) => ipcRenderer.invoke('prefs:set'),
});
```

渲染进程里的 `ReaderCore` 通过 preload 接口间接使用 Node 能力，保持安全边界。

## 8. 版本管理策略

### 阶段一：统一版本（推荐初期使用）

`core`、`extension`、`desktop` 共享同一个版本号。

- 优点：发布流程简单，用户认知统一。
- 缺点：某次仅修复扩展小 bug 时，桌面端也会跟随升版本。

```json
// 所有 packages/*/package.json 的 version 保持一致
{ "version": "1.5.0" }
```

### 阶段二：独立版本（项目成熟后）

核心包独立发版，壳按需升级。

```json
// packages/core/package.json
{ "version": "2.3.1" }

// packages/extension/package.json
{
  "version": "1.5.0",
  "dependencies": {
    "@md-reader/core": "^2.3.0"
  }
}
```

建议通过 `.changeset/config.json` 配置哪些包参与统一版本、哪些独立。

## 9. 迁移路线图

### 第一步：搭建 Monorepo（1-2 天）

- 创建 `packages/core`、`packages/extension`、`packages/desktop`。
- 将现有扩展代码整体移入 `packages/extension`。
- 配置 pnpm workspace、根目录脚本、共享 tsconfig。

### 第二步：抽取核心（3-5 天）

- 将 `src/markdown/renderer.js` 迁移至 `packages/core/src/renderer/`。
- 将样式迁移至 `packages/core/src/themes/`。
- 将配置 schema 与默认值迁移至 `packages/core/src/config/`。
- 扩展壳引入 `@md-reader/core` 并验证功能一致。

### 第三步：实现平台抽象（2-3 天）

- 定义 `FileProvider`、`StorageAdapter` 接口。
- 扩展壳实现 `ChromeFileProvider`、`ChromeStorageAdapter`。
- 验证扩展仍能正常读取本地文件与保存偏好。

### 第四步：桌面 MVP（5-7 天）

- 用 Electron 创建最小窗口，加载基于 `ReaderCore` 的渲染页。
- 实现 `NodeFileProvider` 与本地 JSON 存储。
- 支持打开本地 `.md` 文件、主题切换、自动刷新。

### 第五步：桌面完善（2-4 周）

- 文件关联、右键菜单、最近文件。
- 菜单栏、快捷键、导出 PDF。
- 自动更新、签名、安装包构建。

### 第六步：评估 Tauri 迁移（可选）

- 如果 Electron 体积或性能成为瓶颈，再评估迁移到 Tauri。
- 由于核心包已经平台无关，迁移成本主要集中在主进程。

## 10. 风险与注意事项

### 10.1 核心包不能依赖平台 API

`chrome.storage`、`chrome.runtime`、`node:fs`、`window.electron` 等调用必须留在壳里。核心包只通过注入接口使用能力。

### 10.2 安全边界

- 桌面端如果支持自定义 CSS/JS，必须严格沙箱化渲染进程。
- DOMPurify 配置在核心包里统一维护，不要各壳自行实现。

### 10.3 路径与协议差异

- 扩展中资源路径是 `file://` 或 `chrome-extension://`。
- 桌面端是本地绝对路径或自定义协议（如 `app://`）。
- `resolveAssetPath` 接口由各自平台实现，核心包不假设路径格式。

### 10.4 自动刷新策略

- 扩展：轮询为主，间隔可配置。
- 桌面端：原生文件监听为主，轮询为兜底。
- 核心包只关心 "文件变化时回调触发"，不关心触发方式。

### 10.5 分发成本

- macOS 需要 Apple Developer 账号、签名、Notarization。
- Windows 推荐代码签名证书，否则 SmartScreen 会提示。
- 浏览器扩展需要遵循各商店审核政策。

## 11. 决策清单

在真正开始编码前，建议先确定以下事项：

- [x] 桌面端首屏技术选型：Electron 还是 Tauri？答：Tauri
- [x] 是否统一版本号？初期建议统一。答：统一版本号
- [x] 是否引入 changesets 管理版本与 changelog？答：引入
- [x] 桌面端是否支持自定义 CSS/JS？（涉及安全设计）答：不支持
- [x] 是否先保留现有扩展不动，新建 monorepo 逐步迁移？答：保留现有扩展不动，新建 monorepo 逐步迁移
- [x] 是否有 Apple Developer 账号与 Windows 代码签名证书预算？答：没有
