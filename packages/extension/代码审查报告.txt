一、项目概述
-------------------------------------------------------------
Markdown Reader Pro 是一个 Manifest V3 浏览器扩展，用于在 Chrome、Edge 和 Firefox 中渲染 Markdown 文件。
技术栈: JavaScript (ESM), esbuild, Vitest, jsdom
代码行数: ~800行 (src/), ~120行 (tests/)
测试状态: 19个测试全部通过

二、总体评价
-------------------------------------------------------------
代码质量: 良好
架构设计: 合理，模块职责清晰
可维护性: 良好
安全性: 良好（有XSS防护）
跨浏览器兼容性: 良好（Chrome/Firefox双兼容）

3.1 架构与模块设计 (src/)
-------------------------------------------------------------

[background.js]
- 职责: Service Worker，处理扩展安装时的默认设置初始化
- 优点: 简洁明了，仅做必要工作
- 注意: 代码量过少，可考虑在后续版本中添加更多后台逻辑（如消息处理）

[content-script.js]
- 职责: 内容脚本，负责页面注入、渲染、事件绑定
- 优点:
  * 模块函数拆分清晰（mountReader, bindReaderEvents, renderReader等）
  * 使用模板字符串构建DOM，避免依赖额外模板引擎
  * 有完善的错误回退机制（showFallbackError）
  * 自动刷新功能有协议限制（仅file:协议），安全性考虑到位
- 潜在问题:
  * 第56行: document.title = document.title || inferTitle(...) || '...'
    - 逻辑上如果document.title已经存在，不会使用inferTitle的结果
    - 建议: 如果目的是用Markdown标题增强现有标题，考虑拼接而非替换
  * 第135-138行: chrome和browser的openOptionsPage调用顺序
    - 两个API都调用了一次，虽然其中一个会undefined，但建议显式判断
  * 第143-146行: TOC链接点击处理
    - 使用了history.replaceState但没有处理hashchange事件
    - 如果用户手动刷新页面，hash会丢失（这不是大问题）
  * 第161-174行: refreshFromSource
    - 当response.ok但内容相同时，仍调用renderReader（第168-169行判断了nextMarkdown !== renderedMarkdown）
    - 注意nextMarkdown和renderedMarkdown的比较：如果原始内容有前后空白差异，可能导致不必要的重渲染
    - 建议: 可以考虑trim后比较
  * 第177-186行: startAutoRefresh
    - 使用setInterval而不是setTimeout+递归
    - 如果refreshFromSource执行时间超过2秒，可能导致并发请求
    - 建议: 使用setTimeout递归模式，或添加刷新状态锁
  * 缺少: 未处理扩展被禁用/卸载时的清理逻辑

[preferences.js]
- 职责: 偏好设置的读写和验证
- 优点:
  * 默认值使用Object.freeze，防止意外修改
  * 使用SUPPORTED_KEYS过滤非法键，安全性好
  * storageGet/storageSet函数处理了Chrome旧版回调API兼容
- 潜在问题:
  * normalizePreferences函数（第37-42行）没有对值进行类型校验
    - 例如如果stored.theme = 123（数字），会直接合并，可能导致后续逻辑出错
    - 建议: 对每个键的值进行类型校验
  * storageGet/storageSet中的try-catch过于宽泛
    - 第57行和第83行的try-catch会吞掉所有错误
    - 在开发和调试时可能隐藏问题

[url-detection.js]
- 职责: URL和文档内容检测
- 优点:
  * 使用Set数据结构，查找效率高
  * URL解析有异常处理
  * isProbablyRawMarkdownDocument的启发式检测逻辑合理
- 潜在问题:
  * 第18行: [...MARKDOWN_EXTENSIONS].some((extension) => path.endsWith(extension))
    - 这里用扩展运算符把Set转为数组，其实可以直接用for...of遍历Set，或保持为数组
    - 不是性能问题，只是略显冗余
  * 第26行: doc.body?.dataset?.mdReaderRendered === 'true'
    - 这个检测是为了避免重复渲染，但如果页面是通过JS动态修改的，可能不够鲁棒
  * 第37-45行: looksLikeMarkdown的正则检测
    - 正则可以匹配但无法排除，可能导致误判（如包含代码片段的HTML页面）
    - 这不是严重问题，只是启发式检测的固有局限
  * 第51-55行: getRawMarkdownFromDocument
    - 当body.children.length === 1且是PRE时，提取pre.textContent
    - 但如果PRE内有HTML标签（如语法高亮的span），textContent会丢失标签
    - 对于Markdown渲染场景，这应该是期望的行为

[renderer.js]
- 职责: Markdown渲染引擎
- 优点:
  * 使用markdown-it及丰富的插件生态
  * 自定义KaTeX插件实现，支持行内和块级数学公式
  * DOMPurify清洗HTML，防止XSS
  * 外部链接自动添加target="_blank"和rel="noopener noreferrer"
  * slugify函数支持Unicode字符（使用\p{Letter}\p{Number}）
- 潜在问题:
  * 第14行: CUSTOM_CSS_IMPORT_RE使用了/gim标志
    - global标志(g)配合String.replace使用时，如果多次调用同一个正则对象，可能因lastIndex导致问题
    - 但这里每次调用parseCustomCssImports都会创建新的正则实例，所以安全
  * 第30行: options.sanitize === false ? rendered : sanitizeHtml(rendered)
    - sanitize选项默认为true（非false即清洗），这是安全的设计
  * 第39-55行: extractToc
    - 使用template元素解析HTML，在jsdom环境中工作良好
    - 但cloneNode和querySelectorAll的操作对大量标题可能较慢
  * 第64-74行: highlight函数
    - 当语言不存在时fallback到highlightAuto，这是合理的设计
    - 但hljs.highlightAuto可能性能较差，对大量代码块可能成为瓶颈
  * 第79-88行: fence覆盖
    - 保留了defaultFence并通过.bind绑定，这是正确的做法
  * 第137-152行: katexPlugin
    - math_inline规则在行内数学公式前检查$符号
    - 第155行: state.src[state.pos + 1] === '$' 用于排除$$开头的情况
    - 但如果文本是"$"（单个$）后面没有结束符，第163行的转义检查可能不正确
    - 建议: 考虑使用更完整的行内数学解析器，当前实现可能遗漏一些边界情况
  * 第188-235行: mathBlock
    - 第213行: line.lastIndexOf('$$') 查找闭合标记
    - 如果一行中有多个$$（如示例说明），只会取最后一个
    - 第222-226行: content拼接使用trim()，可能意外删除用户意图的前导/尾随空行
  * 第245-260行: externalLinkRenderer
    - 正确检查http/https协议
    - 但data:和javascript:协议的链接也会被处理（不会被添加target="_blank"）
    - 建议: 考虑将非http链接也添加noopener属性，或进一步限制
  * 第271-280行: slugify
    - 第276行: .replace(/[^\p{Letter}\p{Number}\s_-]/gu, '')
    - 这个正则会移除所有非字母数字下划线和连字符的字符，包括中文标点
    - 对于中文标题，可能导致空slug（如果全是中文标点）
    - fallback到'section'是安全的

[theme-assets.js]
- 职责: 主题样式管理
- 优点:
  * 封装了主题切换的DOM操作
  * 处理了旧版主题link的清理
  * 使用dataset标记样式类型，便于查询
- 潜在问题:
  * 第24行: ensureThemeStyles默认参数doc = document
    - 在Node环境中（如测试）document不存在，但测试传入了mock document
    - 这不是问题，只是需要注意运行时环境
  * upsertStylesheet会每次都设置link.dataset[dataset] = 'true'
    - 对已存在的link这是冗余操作，但无害

[options.js]
- 职责: 扩展选项页面逻辑
- 优点:
  * 表单读写逻辑简单清晰
  * 重置功能恢复默认值并保存
- 潜在问题:
  * 缺少表单验证逻辑
  * 没有处理chrome.storage API不可用的情况（但preferences.js已经处理了）

四、安全问题
=============================================================

[已防护]
1. XSS: 使用DOMPurify清洗渲染后的HTML
2. 外部链接: 自动添加noopener noreferrer
3. Mermaid: securityLevel设置为'strict'
4. 自动刷新: 限制在file:协议下
5. 存储: 过滤非法配置键

[潜在风险]
1. custom CSS注入 (injectCustomCss):
   - 获取的CSS内容直接注入为style标签，未做CSS净化
   - 恶意CSS可能包含@expression(IE)或其他攻击向量
   - 风险等级: 低（需要用户主动在Markdown中声明@import）

2. fetch请求 (refreshFromSource):
   - 使用fetch获取页面内容，可能携带cookies
   - 对于需要认证的URL，2秒轮询可能导致请求过于频繁
   - 风险等级: 低

3. 数学公式注入:
   - KaTeX renderToString可能渲染恶意LaTeX（虽然KaTeX有限制）
   - 已通过try-catch处理错误
   - 风险等级: 极低

五、性能问题
=============================================================

1. renderMarkdown每次调用都创建新的MarkdownIt实例
   - 第28行: const md = createMarkdownIt()
   - 建议: 如果配置不变，可以缓存实例

2. extractToc每次创建template元素并解析HTML
   - 第40-41行: document.createElement('template')
   - 在已有DOM的情况下，可以直接查询而不是重新解析

3. ensureThemeStyles每次都查询和更新DOM
   - 如果主题没有变化，这些DOM操作是冗余的
   - 建议: 缓存当前主题，仅在变化时更新

4. highlightAuto的自动检测
   - 对于没有指定语言的大量代码块，自动检测可能较慢
   - 建议: 提供一个"无语言时不高亮"的选项
