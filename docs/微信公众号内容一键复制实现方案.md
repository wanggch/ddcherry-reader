# 微信公众号内容一键复制实现方案

> 日期：2026-07-16  
> 状态：待确认  
> 适用范围：Markdown Reader Pro 桌面客户端（macOS / Windows）  
> 本文仅描述实现方案，不包含代码改动

## 1. 结论摘要

推荐在桌面客户端增加“复制到公众号”按钮，将当前 Markdown 重新转换为一份独立于阅读主题的“公众号安全 HTML”，再通过 Tauri 原生富文本剪贴板尝试写入 `text/html` 和 `text/plain`。用户进入微信公众平台编辑器后直接粘贴即可。

不建议直接复制当前预览区 DOM，也不建议首版承诺本地图片、Mermaid 和数学公式可以随整篇文章一次性可靠粘贴。原因是当前预览 DOM 混有阅读器控件并依赖外部 CSS，而多个本地二进制图片无法通过一份 HTML 剪贴板内容可靠传递给公众号编辑器。

首版推荐的产品边界：

| 项目 | 首版结论 |
|---|---|
| 入口 | 桌面客户端工具栏“复制到公众号”；原生菜单提供同一命令 |
| 剪贴板 | 使用 Tauri `writeHtml(html, plainText)`，不依赖 WebView 的 `navigator.clipboard` |
| 导出主题 | 固定的公众号安全浅色主题，不跟随阅读器当前主题 |
| 目标支持（待阶段 0 实测） | 标题、段落、粗体、斜体、删除线、列表、引用、分隔线、代码块、简单表格、脚注、提示块 |
| 图片 | 由微信文章图片上传流程返回并通过实测的 URL 可保留；普通 HTTPS 图片尽力保留；本地、相对、`data:`、`blob:`、Tauri 地址不复制并生成明确占位与警告 |
| Mermaid | 首版转为带说明的源码块或占位，不复制当前 SVG |
| 数学公式 | 首版转回 LaTeX 文本或占位，不复制依赖 KaTeX 字体和样式的 HTML |
| Frontmatter | 默认不复制 |
| 自定义 CSS | 不复制，防止不兼容样式和不可信样式进入公众号内容 |
| Raw 模式 | 仍导出渲染后的公众号内容，不复制 Markdown 源码 |
| 浏览器扩展 | 首版不接入，但转换模块放在共享核心，后续可复用 |

## 2. 目标与非目标

### 2.1 目标

- 用户点击一次即可把当前文档的正文和常见排版写入系统富文本剪贴板。
- 粘贴到微信公众号编辑器后，不依赖本项目 CSS、字体、脚本或运行时能力。
- 在 macOS 和 Windows 上使用同一套内容转换规则。
- 对不能可靠复制的内容明确告知，不静默丢失。
- 转换逻辑集中在共享核心中，可单元测试，也可供浏览器扩展后续复用。
- 输出内容遵守微信公众平台当前公开的文章结构、CSS、字体和 Dark Mode 建议。

### 2.2 首版非目标

- 不自动登录微信公众平台。
- 不自动创建草稿、填写标题、作者、摘要或封面。
- 不在桌面客户端保存公众号 `AppSecret`。
- 不保证任意自定义 HTML 和自定义 CSS 原样保留。
- 不保证任意第三方图片地址会被微信自动转存。
- 不提供多个公众号排版模板；首版只提供一套稳定样式。
- 不把“刚粘贴时看起来正确”作为唯一成功标准，内容还需通过保存、重新打开、预览和移动端检查。

## 3. 当前项目基础与约束

### 3.1 可复用的现有结构

项目已经采用 pnpm workspace：

- `packages/core`：Markdown 渲染、主题、通用阅读 UI。
- `packages/desktop`：Tauri 2 桌面壳，目标平台为 macOS 和 Windows。
- `packages/extension`：浏览器扩展壳。

当前桌面端每个标签页持有一个 `ReaderCore`，活动文档可通过 `TabManager.activeTab` 获取。工具栏动作通过 `ReaderCoreOptions` 回调交给桌面壳处理，PDF 导出已经采用这一模式，因此“复制到公众号”可以沿用同一接入点。

### 3.2 不能直接复用的部分

1. `ReaderCore.exportToHtml()` 当前实际返回的是 Markdown 源文，不是 HTML，不能作为本功能的导出入口。
2. 当前预览样式主要依赖 `reader.css`、CSS 变量和 class。只复制 `innerHTML` 会丢失排版。
3. 预览 DOM 在渲染后增加了代码复制按钮、代码行号、Mermaid 全屏控件等阅读器专用节点。
4. 当前图片处理只添加懒加载属性，没有把相对图片路径转换为跨应用可访问的地址。
5. Mermaid 在预览区会被渲染为 SVG；KaTeX 输出依赖 class、外部样式和字体。两者都不适合直接序列化到公众号剪贴板。
6. 当前剪贴板能力只有 `navigator.clipboard.writeText()`，只能写纯文本。
7. 自定义 CSS 会直接注入阅读页面。公众号导出不得把这些样式整体带入剪贴板。

## 4. 微信编辑器与剪贴板约束

### 4.1 富文本剪贴板

系统剪贴板的目标内容包含：

- `text/html`：公众号编辑器优先使用的富文本内容。
- `text/plain`：粘贴到纯文本目标时的可读降级内容。

Tauri 2 官方剪贴板插件提供：

```ts
writeHtml(html: string, altText?: string): Promise<void>
```

该能力在桌面端支持 HTML，并由原生插件处理 macOS Pasteboard 和 Windows `CF_HTML` 格式。与 Web Clipboard API 相比，它不依赖 WKWebView / WebView2 对 `ClipboardItem` 的实现差异、用户激活时机或网页剪贴板权限，因此应作为桌面端唯一主路径。

`writeHtml` 不是事务式接口。底层可能按顺序写入 HTML 和纯文本，失败时不能承诺剪贴板完全不变，个别平台也可能只留下纯文本降级内容。客户端只能根据调用结果提示“写入成功”或“写入异常”，不能在不读取剪贴板的前提下证明两个 MIME 都已写入。阶段 0 必须在 macOS、Windows 和真实公众号编辑器中分别验证富文本及纯文本表现。

能力权限只开放 `clipboard-manager:allow-write-html`，不开放读取剪贴板权限。

### 4.2 微信文章结构与样式

导出内容遵守以下规则：

- 使用有效、浅层的 HTML 结构，相同标签不嵌套超过 15 层。
- 只使用内联 CSS，不依赖 `<style>`、外部样式表、class 或 CSS 变量。
- 不设置自定义 `font-family`，使用公众号默认字体栈。
- 不使用固定容器宽高、绝对定位、变形布局、`line-height: 0`、`!important`。
- `text-align` 只使用 `left`、`right`、`center`，不使用 `start` / `end`。
- 普通正文不使用 `<pre>`；只有代码块使用 `<pre>`，并强制自动换行。
- 使用中等对比度的浅色样式，兼顾微信 Dark Mode 的颜色转换。
- 不依赖 JavaScript、事件属性、动画或运行时脚本。

微信没有公开稳定的“从系统剪贴板粘贴时保留哪些标签和 CSS”的完整白名单。因此具体兼容性必须以真实公众号编辑器的验证结果为准，不能只依赖浏览器中预览结果。

### 4.3 图片的硬限制

一份 HTML 剪贴板数据可以引用图片 URL，但不能把文章中的多张本地图片作为独立二进制附件一并可靠传给粘贴目标。

| 图片来源 | 首版处理 |
|---|---|
| 由微信文章图片上传流程返回并通过实测的 URL | 保留 `<img>` |
| 普通公网 HTTPS URL | 保留但标记为“尽力兼容”，需要保存和发布验证 |
| 相对路径、本地绝对路径 | 替换为可见占位，并在复制结果中警告 |
| `asset:`、`http://asset.localhost`、Tauri 自定义协议 | 替换为占位 |
| `blob:` | 替换为占位 |
| `data:` | 首版替换为占位，避免被微信过滤或导致剪贴板过大 |
| SVG | 首版不保证，普通 SVG 图片按不支持处理 |

真正保证本地图片、Mermaid 和公式随文章一键进入公众号，需要先把它们转成 JPG / PNG，再上传到微信文章图片接口并替换为微信返回的 URL。这会引入公众号授权、服务端 `access_token` 管理和图片上传后端，不应在首版里假装通过剪贴板解决。微信接口当前还要求图片格式和大小满足其限制，直接创建草稿时另需封面 `thumb_media_id`、标题、正文等字段；这些约束以实施时的官方文档为准，并在阶段 3 单独设计。

## 5. 方案比较

### 5.1 方案 A：复制当前预览 DOM

流程：克隆 `.md-reader-content`，拷贝当前计算样式后写入剪贴板。

优点：

- 初始实现看似较快。
- 能拿到已渲染的 Mermaid SVG 和 KaTeX DOM。

缺点：

- 会耦合阅读器 DOM 和后处理控件。
- `getComputedStyle()` 会产生大量 WebView 特有、无效或危险的样式。
- 深色主题、自定义 CSS、布局宽度会污染公众号内容。
- 阅读器 UI 一旦变化，导出结果也可能回归。
- Mermaid SVG 和 KaTeX 即使被复制，也不代表微信会稳定保存和发布。

结论：不采用。

### 5.2 方案 B：从 Markdown 生成公众号专用 HTML

流程：读取当前 Markdown，复用现有 Markdown 渲染结果，在独立 DOM 中做公众号语义转换、样式内联、资源检查和二次清洗。

优点：

- 输出稳定，不受当前阅读主题和预览 UI 影响。
- 可以为每种 Markdown 元素定义清晰的兼容策略。
- 容易构造固定输入输出测试。
- 可以明确识别和报告不支持内容。
- 核心转换能力可供桌面端和扩展端复用。

缺点：

- 需要维护公众号样式映射。
- Mermaid、公式、图片仍需单独制定策略。

结论：推荐采用。

### 5.3 方案 C：直接调用微信公众号草稿 API

流程：客户端把内容和图片上传到微信，直接创建草稿，不经过剪贴板。

优点：

- 可以严格处理图片和素材。
- 最终可做到真正的一键创建草稿。

缺点：

- 已超出“复制后粘贴”的需求。
- 需要公众号开发权限、授权流程、服务端 token 和安全后端。
- 不能把 `AppSecret` 打包或明文保存在桌面客户端。
- 运维、隐私和失败恢复成本显著增加。

结论：作为后续完整版本，不作为首版。

## 6. 推荐架构

```text
┌──────────────────────────────────────────────────────┐
│ ReaderCore                                            │
│ 当前有效 Markdown + 当前文件上下文                     │
└──────────────────────────┬───────────────────────────┘
                           │ copyForWechat()
                           ▼
┌──────────────────────────────────────────────────────┐
│ WeChat Exporter（packages/core）                      │
│ 渲染 -> 语义转换 -> 资源检查 -> 样式内联 -> 二次清洗   │
└──────────────────────────┬───────────────────────────┘
                           │ { html, text, warnings }
                           ▼
┌──────────────────────────────────────────────────────┐
│ Desktop Clipboard Writer（packages/desktop）          │
│ Tauri writeHtml(html, text)                           │
└──────────────────────────┬───────────────────────────┘
                           │ 系统富文本剪贴板
                           ▼
                  微信公众平台编辑器粘贴
```

### 6.1 核心转换模块

建议先新增一个内部模块：

```text
packages/core/src/export/wechat.ts
```

转换、样式映射、资源策略、清洗和纯文本生成先放在同一模块中，避免在兼容性白名单尚未稳定前建立过多文件和浅接口。后续某部分足够独立且明显增长时，再按职责拆分内部实现；对外接口不变。

对调用者保持一个小接口：

```ts
interface WechatClipboardPayload {
  html: string;
  text: string;
  warnings: WechatExportWarning[];
}

class ReaderCore {
  copyForWechat(): Promise<WechatClipboardPayload>;
}
```

调用者不需要知道标签映射、CSS 白名单、资源分类或清洗规则。`ReaderCore` 内部快照 `renderedMarkdown` 和当前文件路径，生成 payload 后调用注入的桌面写入函数，并负责工具栏状态和警告反馈。这里明确使用 `renderedMarkdown`，因为当前文件自动刷新只更新该字段；使用 `currentMarkdown` 会复制到旧内容。该状态问题也可在实现前直接合并为一个权威 Markdown 字段。

首版只有 Tauri 一种富文本写入实现，因此不提前设计通用 `ClipboardAdapter` 接口。桌面层使用一个具体的 `writeWechatClipboard(payload)` 函数即可；等浏览器扩展也接入并出现第二种实现时，再抽取真实平台 seam。

### 6.2 桌面端接入

`ReaderCoreOptions` 增加可选回调：

```ts
onWriteWechatClipboard?: (payload: WechatClipboardPayload) => Promise<void>;
```

只有传入回调时才显示“复制到公众号”按钮，避免浏览器扩展在未支持富文本剪贴板时出现无效入口。

桌面端流程：

1. 工具栏点击或原生菜单发出复制命令。
2. `TabManager` 定位活动标签页。
3. 调用 `activeTab.core.copyForWechat()`；工具栏也调用同一个公开方法。
4. `ReaderCore` 建立快照、生成 payload，并调用 `onWriteWechatClipboard(payload)`。
5. 桌面实现调用 Tauri `writeHtml(payload.html, payload.text)`。
6. `ReaderCore` 根据调用结果和 payload warnings 显示成功、警告或失败状态。

不使用普通 `Cmd/Ctrl+C`，避免破坏用户选中文本后的常规复制行为。首版也不默认增加新快捷键。

### 6.3 Tauri 插件

预计增加：

- JavaScript 依赖：`@tauri-apps/plugin-clipboard-manager`。
- Rust 依赖：`tauri-plugin-clipboard-manager`。
- 在 Tauri Builder 中注册插件。
- capability 增加 `clipboard-manager:allow-write-html`。

不授予 `read-text`、`read-image`、`read-html` 等读取权限。

## 7. 内容转换管线

### 7.1 总体步骤

1. 对权威 Markdown（当前实现为 `renderedMarkdown`）和文件路径建立只读快照，避免文件自动刷新导致一次导出前后内容不一致。
2. 去掉自定义 CSS import，提取并默认忽略 frontmatter。
3. 调用现有 `renderMarkdown(markdown, { sanitize: true })` 获取基础 HTML。
4. 使用未挂载到实时 DOM 的 `<template>` 解析 HTML，保持内容惰性；先删除或重写 `src`、`srcset`、背景 URL 等资源属性，整个转换过程不把未处理节点插入页面。
5. 按元素语义转换为公众号结构并添加固定内联样式。
6. 清除阅读器 wrapper、class、`id`、`target`、懒加载属性和无关 `data-*` 属性。
7. 检查图片、链接、Mermaid、公式等特殊资源，替换不支持内容并记录结构化警告。
8. 用导出专用 DOMPurify 白名单再次清洗，不复用阅读器相对宽松的清洗配置。
9. 序列化为 HTML fragment，同时生成语义等价的纯文本。
10. 交给桌面壳调用 `writeHtml` 尝试写入富文本和纯文本剪贴板。

### 7.2 为什么不读取当前 DOM

导出从 Markdown 快照重新生成，而不是克隆 `.md-reader-content`。这样可以自然避开：

- `.md-reader-code-header` 代码复制按钮。
- `.md-reader-code-line-numbers` 行号。
- `.md-reader-code-wrapper` 阅读器布局。
- Mermaid 灯箱与全屏按钮。
- 当前主题变量和内容卡片宽度。
- 用户导入的自定义 CSS。

### 7.3 HTML 与样式映射

| Markdown 内容 | 导出策略 |
|---|---|
| `h1` | 保留为正文内一级标题样式，不自动猜测并删除文章标题 |
| `h2` / `h3` | 使用浅层 `section` 或 `p` + `strong`，内联字号、颜色和间距 |
| `h4` - `h6` | 逐级弱化，但避免过多字号层级 |
| 段落 | `p`，设置稳定行高和上下间距，不设置字体族 |
| 粗体 / 斜体 / 删除线 | 保留语义标签，补充最少内联样式 |
| 有序 / 无序列表 | 保留 `ol` / `ul` / `li`，只允许一层嵌套进入保证范围 |
| 任务列表 | 转换为文本符号 `☑` / `☐`，删除不可编辑的 checkbox |
| 引用 | 左边框 + 浅背景 + 内边距，不使用固定宽度 |
| 行内代码 | `code` + 浅背景、边框、自动断词 |
| 代码块 | `<pre><code>`，`white-space: pre-wrap; overflow-wrap: anywhere`，删除行号和复制按钮 |
| 高亮代码 | token 颜色内联；不依赖 Highlight.js class，首版可先只保证纯代码排版 |
| 表格 | `width: 100%; table-layout: fixed; border-collapse: collapse`，每个单元格内联边框与内边距 |
| 超宽表格 | 产生警告；首版不做截图或复杂重排 |
| 脚注 | 保留为文章末尾普通编号列表，删除页面内锚点跳转依赖 |
| 提示块 | 转换为统一的边框提示块，降低不同 admonition 类型的视觉复杂度 |
| `<details>` | 展开为普通内容，不保留交互折叠能力 |
| TOC | 删除自动目录和页内锚点；公众号正文通常不需要阅读器目录 |
| 自定义 HTML | 仅保留白名单中的语义元素和安全属性，其余展开或删除 |
| Frontmatter | 默认忽略，不作为正文代码块复制 |

### 7.4 链接策略

- 普通链接只允许 `https:` 进入目标支持路径。
- 微信文章链接和普通 HTTPS 链接保留可见文本与 `href`，但普通外链标记为尽力兼容。
- 图片按原始 Markdown URL 分类，不先经过浏览器解析。由微信图片上传接口返回的已验证 URL 按原值保留；普通图片仅接受 HTTPS。
- 相对链接、`file:`、`javascript:`、`blob:`、`data:`、`asset:`、`http://asset.localhost` 和配置的 Tauri 自定义协议移除 `href` 或 `src`，保留可见文本或图片占位。
- `text/plain` 中使用“文本（URL）”形式，避免纯文本降级时丢失地址。
- 删除 `target="_blank"` 和阅读器添加的 `rel`，交给微信编辑器统一处理。

### 7.5 Mermaid 与公式策略

首版不复制预览 DOM 中的 Mermaid SVG 和 KaTeX HTML：

- Mermaid：转换成“图表未复制”占位，并可附 Mermaid 源码代码块；记录警告。
- 行内公式：尽可能从 KaTeX annotation 取回 LaTeX，输出 `$...$` 文本。
- 块公式：输出带说明的 LaTeX 代码块或占位；记录警告。

后续完整版本将 Mermaid 和公式渲染到带不透明背景的 PNG，上传到微信后再插入普通 `<img>`。

## 8. 用户交互

### 8.1 工具栏状态

按钮状态：

- 默认：`复制到公众号`
- 处理中：`正在生成…`，按钮禁用，防止重复触发
- 成功：`已复制`，约 1.5 秒后恢复
- 失败：`复制失败`，同时显示可读错误信息

### 8.2 结果反馈

使用 `aria-live="polite"` 的轻量状态提示：

- 无警告：`已复制，可粘贴到公众号编辑器`
- 有警告：`已复制；2 张本地图片和 1 个 Mermaid 图未包含`
- 失败：`复制异常，请重新复制；系统剪贴板可能只写入了部分格式`

首版先完成复制再展示警告，不增加复制前确认框，保持真正的一键操作。占位内容会出现在原内容位置，避免用户只看到提示却不知道缺失位置。

### 8.3 原生菜单

建议在 Edit 菜单增加 `Copy for WeChat Official Account`，路由到活动标签页的同一命令。若当前没有活动文档则禁用或无操作并提示。

工具栏和菜单必须调用同一个应用层方法，不能各自实现转换或剪贴板逻辑。

## 9. 安全与隐私

- Markdown 中的原始 HTML先经过现有清洗，再经过导出专用白名单清洗。
- 导出清洗只允许必要标签、属性、协议和有限 CSS 属性。
- 删除 `script`、事件属性、`style` 标签、外部样式、表单、iframe、音视频等非文章元素。
- 不复制阅读器自定义 CSS，不批量序列化 `getComputedStyle()`。
- 首版转换全程本地执行，不上传文章正文，不调用第三方排版服务。
- 不在运行时自动调用微信结构验证接口，避免在用户不知情时传出正文；该接口只用于开发阶段的人工样例验证。
- Tauri 只开放 HTML 写入权限，不开放任何剪贴板读取权限。
- 如果后续接入微信图片 API，`AppSecret` 和 `access_token` 必须在受控后端管理，不进入桌面安装包、日志或本地明文配置。

## 10. 错误与降级策略

| 场景 | 行为 |
|---|---|
| 没有活动文档 | 不写剪贴板，提示“请先打开文档” |
| HTML 生成失败 | 尚未调用剪贴板，不覆盖现有内容，显示失败原因 |
| 原生 HTML 剪贴板写入失败 | 明确提示写入异常；由于底层非事务式，剪贴板可能未改变，也可能已写入部分格式 |
| 文档含不支持图片 | 其位置写入占位，复制整体继续完成并返回警告 |
| 文档含恶意或非法 HTML | 删除非法内容，必要时记录“部分 HTML 已清理”警告 |
| 内容为空 | 不写剪贴板，提示“当前文档没有可复制内容” |
| 文档自动刷新 | 使用点击瞬间的 Markdown 快照完成本次导出 |
| 内容很大 | 显示处理中状态；超过约定上限时提示用户拆分文章，不无限制生成超大剪贴板 |

是否设置具体大小上限，应在真实公众号编辑器压测后决定，不在方案阶段猜测微信的硬限制。

### 11.4 首版验收标准

- macOS 与 Windows 点击一次后，公众号编辑器可以粘贴出富文本而不是 HTML 源码。
- 标题、段落、列表、引用、代码块和简单表格在保存并重新打开草稿后仍可读。
- 输出不依赖项目 CSS，切换阅读器深色主题不会改变导出主题。
- 阅读器工具栏、侧边栏、代码复制按钮、行号和 Mermaid 控件不会进入文章。
- 危险脚本、事件、URL 和非白名单样式不会进入剪贴板 HTML。
- 不支持的图片、Mermaid、公式不会静默消失，原位置有占位且界面有汇总警告。
- 纯文本目标能粘贴出可读正文和链接地址。
- 微信移动端浅色与 Dark Mode 下不存在不可见文字、固定宽度溢出或普通段落不换行。

## 12. 分阶段实施

### 阶段 0：兼容性原型

目的：在正式开发前消除最高风险假设。

- 用 Tauri `writeHtml` 写入最小 HTML + 纯文本，分别确认富文本目标和纯文本目标得到的格式。
- 用真实公众号编辑器验证段落、列表、代码、表格、链接、远程图片。
- 验证保存、重新打开、预览、移动端和 Dark Mode，而不只看粘贴瞬间。
- 固化首版允许的标签与 CSS 属性集合。

输出：一份实际兼容性记录和最终样式白名单。

### 阶段 1：首版一键复制

- 实现共享核心 `WeChat Exporter`。
- 实现固定安全主题、资源检查、二次清洗、纯文本降级和结构化警告。
- 接入 Tauri 原生富文本剪贴板。
- 增加工具栏按钮、原生菜单和状态反馈。
- 完成核心与桌面自动测试。
- 完成真实公众号编辑器验收矩阵。

粗略工作量：4 至 6 个工程日，真实微信环境验证时间另计。

### 阶段 2：排版增强

- 根据实测结果完善代码高亮和复杂表格降级。
- 增加公众号导出预览和警告详情。
- 评估增加少量经过验证的样式模板。
- 评估浏览器扩展接入 Web Clipboard API；桌面端仍保留 Tauri 原生路径。

### 阶段 3：完整图片与图表

- 阶段 3 只在首版验证后另行设计，不属于本方案的已确认实施范围。
- 建立公众号授权和安全后端，不在客户端保存 `AppSecret`。
- 按实施时官方限制把本地图片规范化、压缩为受支持格式和大小，再通过服务端上传到微信文章图片接口。
- Mermaid 和公式渲染为带安全背景的 PNG 后上传。
- 用微信返回 URL 替换全部图片，再写入剪贴板；若改为直接创建草稿，还需设计封面素材、标题、摘要、正文限制和失败恢复。
- 增加上传进度、重试、取消、缓存和失败恢复。

阶段 3 的工作量和部署成本显著高于首版，应在确认确实需要“图片也完全一键完成”后单独设计。

## 14. 风险清单

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 微信粘贴规则未完整公开且会变化 | 同一 HTML 后续表现可能变化 | 固定兼容样例，记录验证环境，发布前做冒烟测试 |
| 普通 HTTPS 图片未被微信转存 | 草稿或发布后图片失效 | 首版标记尽力兼容；只有经过微信上传流程并实测的 URL 才进入目标支持范围；后续接上传后端 |
| 原生富文本写入只留下部分格式 | 用户粘贴成纯文本或旧剪贴板内容 | 阶段 0 分平台验证；失败提示不承诺剪贴板未改变；保留重新复制路径 |
| 微信 Dark Mode 改色 | 代码块、引用或图片对比度变差 | 固定浅色安全主题，中等对比度，不使用复杂渐变和透明背景 |
| 复杂 Markdown 产生深层 DOM | 微信删除结构 | 转换为浅层结构，并用官方结构检测接口做开发期验证 |
| 代码和表格在移动端溢出 | 文章不可读 | 自动换行、固定表格布局、长 token 测试、超宽表格警告 |
| 自定义 HTML / CSS 注入 | 安全和排版污染 | 忽略自定义 CSS，导出专用白名单二次清洗 |
| 直接复制预览 DOM 导致耦合 | 阅读器改版破坏导出 | 从 Markdown 快照独立生成公众号 HTML |
| 客户端保存公众号密钥 | 账号安全风险 | 首版无微信鉴权；后续必须由受控后端管理密钥 |

## 15. 待确认决策

建议确认以下默认项后再进入实现：

1. **首版范围**：接受“以文字与常见排版为目标支持；具体标签在阶段 0 实测后固化；本地图片、Mermaid、公式用占位和警告”的方案，而不是首版同时建设微信图片上传后端。推荐接受。
2. **导出主题**：固定公众号安全浅色主题，不跟随当前阅读主题。推荐接受。
3. **Frontmatter**：默认不复制。推荐接受。
4. **一级标题**：保留在正文，不自动删除第一个 `h1`。推荐保留，避免隐式丢内容。
5. **远程图片**：只有由微信文章图片上传流程返回并完成保存、预览、发布实测的 URL 进入目标支持范围；普通 HTTPS 图片尽力保留并提示风险。推荐接受。
6. **Mermaid / 公式**：首版保留源码或占位，后续有图片上传能力后再转 PNG。推荐接受。
7. **平台范围**：首版只接桌面客户端，转换核心保持可复用；浏览器扩展后续再接。推荐接受。
8. **菜单与快捷键**：首版提供工具栏和原生菜单，不占用新的全局快捷键。推荐接受。
